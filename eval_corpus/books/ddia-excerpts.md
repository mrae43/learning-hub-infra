# Designing Data-Intensive Applications — Excerpts

## Chapter 5: Replication

Replication means keeping a copy of the same data on multiple machines that are connected via a network. Reasons for replication include keeping data geographically close to users, allowing the system to continue working even if some of its parts have failed, and scaling out the number of machines that can serve read queries. Replication is one of the core mechanisms a distributed database uses to provide durability and availability: if one machine is lost, another still holds the data. There are three main approaches to replication — single-leader, multi-leader, and leaderless — and they differ in how writes are handled and how data propagates between replicas. The choice between them is a trade-off between write availability, read consistency, and operational simplicity. Most databases let you configure replication per-node or per-cluster, and a single deployment may combine approaches.

The most common approach is called leader-based replication, also known as active/passive or master-slave replication. One replica is designated the leader (also known as master or primary). When clients want to write to the database, they must send their requests to the leader, which first writes the new data to its local storage. The other replicas are called followers (read replicas, slaves, secondaries, or hot standbys). Whenever the leader writes new data to its local storage, it also sends the data change to all followers as part of a replication log or change stream. Each follower takes the log from the leader and updates its local copy of the database accordingly, by applying all writes in the same order as they were processed on the leader. When a client wants to read from the database, it can query either the leader or any follower. However, writes are only accepted on the leader. This asymmetry is what makes the system consistent: there is a single, well-defined order in which writes are applied.

An important trade-off in replicated systems is whether the replication is synchronous or asynchronous. In synchronous replication, the leader waits until the follower has confirmed that it received the write before reporting success to the user, and before making the write visible to other clients. In asynchronous replication, the leader sends the message but doesn't wait for a response from the follower. The advantage of synchronous replication is that the follower is guaranteed to have an up-to-date copy of the data that is consistent with the leader. The disadvantage is that if the synchronous follower doesn't respond, the write cannot be processed at all. If the leader and a synchronous follower both fail, the write is lost entirely. Because of this trade-off, synchronous replication is rarely used in practice; most systems use asynchronous replication with one or more synchronous followers for durability.

When a system uses asynchronous replication, followers lag behind the leader. The lag can be small during normal operation but can grow large if a follower is slow or the leader is overloaded. Reading from a lagging follower can return stale data: a user reads their own recent write from the leader, then reads from a follower that has not yet applied it. This is the read-your-writes consistency problem, and it is a direct consequence of replication lag. Systems mitigate it with read-your-writes, monotonic reads, and consistent-prefix guarantees, each of which is weaker than full serializability but much cheaper to provide. Setting up a new follower can often be done without downtime. Theoretically, you could simply copy the leader's data files to the follower and start replicating from that point. However, copying the files requires a filesystem snapshot consistent with the leader's replication log position. The standard procedure is to take a consistent snapshot of the leader's data, copy it to the new node, record the log position corresponding to that snapshot, and then have the new follower connect and consume all changes that happened after the snapshot. This avoids downtime because the leader keeps serving reads and writes while the snapshot is copied.

## Chapter 6: Partitioning

Partitioning is the splitting of a large dataset into smaller subsets. Each partition is a small database of its own. Reasons for partitioning include scalability and query throughput. Different partitions can be placed on different nodes in a shared-nothing cluster. A database query can potentially be parallelized across many nodes, with each node answering for the subset of data it holds. Partitioning is about sharing the workload, whereas replication is about making copies for durability and read scaling; the two are often combined, with each partition replicated onto several nodes.

One way of partitioning is to assign each key to a partition by taking the hash of the key and then assigning a range of hashes to each partition. This approach is known as hash-based partitioning or consistent hashing. It has the advantage of distributing keys quite evenly across partitions, since a good hash function spreads keys uniformly over the hash space. The downside of hash partitioning is that range queries lose their locality: keys that are adjacent in the key space land in different partitions, so an efficient range scan across many partitions is hard. The opposite approach is range-based partitioning, where keys are assigned to partitions based on their actual value ranges. Range-based partitioning is more effective for range-scan queries and when the data has a natural sort order. However, range partitioning has a skew problem: if the data is not uniformly distributed across the value range, some partitions receive far more writes than others, creating hot spots.

Secondary indexes are the main factor that makes partitioning complicated. The problem is that secondary indexes don't map neatly to partitions. There are two main approaches to partitioning a database with secondary indexes: document-based partitioning (where each partition maintains its own secondary indexes, also known as local indexes) and term-based partitioning (where a global index is partitioned by the indexed term rather than the document). Document-based partitioning keeps writes local but makes queries over secondary indexes scatter to every partition. Term-based partitioning keeps reads local but makes writes slower, because a single write to one document may need to update several partitions' indexes. The choice between them mirrors the general tension in distributed systems: whether to optimise for write locality or read locality, and every design decision about partitioning is really a decision about which queries should be fast.

## Chapter 7: Transactions

The concept of a transaction has been the mechanism for grouping multiple reads and writes into a logical unit. Transactions simplify the programming model by hiding the complexities of concurrency and partial failures. Instead of reasoning about individual statements and what happens if the process crashes halfway through, the application developer can treat a group of operations as atomic: either they all take effect or none of them do. ACID stands for Atomicity, Consistency, Isolation, and Durability. Atomicity means that writes in a transaction are executed as a whole — either all succeed or all fail. Consistency means that the database is in a valid state before and after the transaction. Isolation means that concurrently executing transactions are isolated from each other. Durability means that once a transaction has committed successfully, the data will not be forgotten, even if there is a hardware fault or the database crashes. Atomicity and isolation are about what happens during a transaction, while durability is about what happens after a commit, and consistency is a property of the application's invariants rather than the database alone.

Read Committed is the most basic level of isolation. It guarantees that any data read is committed at the moment it is read — it never sees uncommitted data. Snapshot Isolation (also known as Repeatable Read) gives each transaction a consistent snapshot of the database at a point in time. Serializable isolation is the strongest level; it guarantees that even though transactions may execute concurrently, the end result is the same as if they had executed one at a time, in some serial order. Weaker levels permit anomalies: dirty reads, dirty writes, read skew, write skew, and lost updates. The choice of isolation level is a trade-off between the consistency guarantees an application needs and the performance and concurrency the system can deliver. A system that runs everything at serializable isolation gives the strongest guarantees but pays for it with reduced concurrency, while a system at Read Committed runs fast but leaves the application to handle anomalies itself.

## Chapter 10: Batch Processing

Batch processing is the classic approach to processing large volumes of data. A batch processing job takes a fixed input and produces a fixed output, with no side effects or external interactions during the processing. Because the input is bounded, the job can be run repeatedly and its results compared. Batch jobs are the natural fit for tasks that process all of the data at once — building search indexes, computing aggregates, or training models over a fixed snapshot. MapReduce is a programming model for processing large datasets in a distributed fashion. A MapReduce job has two phases: the mapper and the reducer. The mapper applies a transformation to each input record independently. The reducer aggregates the mapper's outputs. Between the map and reduce phases, the framework sorts and groups the intermediate data by key. The framework handles distribution, fault tolerance, and scheduling, so the application code only defines the map and reduce functions. The key property of MapReduce is that the intermediate result between map and reduce is materialized to disk, which makes it robust against failures at the cost of latency.

## Chapter 11: Stream Processing

Stream processing deals with data that arrives continuously, as opposed to batch processing where the input is bounded. The key difference is that streams are unbounded — you never know when the data will end. This changes the programming model: a stream processor must make decisions based on a potentially infinite sequence of events, without ever seeing the whole input. Stream processors are used for event-driven applications, real-time analytics, and continuously updating materialized views. An event is a small, self-contained record of something that happened at some point in time. Events are written by producers and read by consumers. A stream is the sequence of events ordered by time. Events are immutable: once produced, they are not changed, and new events are appended to the end of the stream. This immutability is what makes event streams safe to replay and to process multiple times, which is valuable for debugging and for recovering from a processing failure.

A log is the most natural representation of an event stream. In the context of stream processing, a log is simply an append-only sequence of records. A log can be partitioned across multiple machines, similar to a partitioned database table. Log-based message brokers (unlike traditional message queues) let multiple consumers read the same stream independently, and they retain the log so consumers can re-read it. This makes the log both a message-passing mechanism and a storage system, which is why log-based brokers sit at the boundary between databases and messaging. The relationship between batch and stream processing is complementary: batch systems compute over bounded data, stream systems compute over unbounded data, and many modern systems blur the line by treating a batch job as a special case of a stream that happens to have a finite input.
